SmartBills Cleaner · Gestión Ágil

Presentación de metodología ágil, roles simulados y desarrollo por sprint

Esta presentación resume cómo se aplicó Scrum en un proyecto desarrollado por una sola persona, adaptando los roles y ceremonias de forma disciplinada. El enfoque se apoya en el backlog del proyecto y en las evidencias de sprint compartidas para mostrar qué se planificó, qué se ejecutó y qué postura metodológica se asumió.

1. Metodología

Metodologías ágiles que se usaron

Base teórica: Scrum + gestión incremental del Product Backlog

Scrum como marco principal

Se trabajó con una lógica iterativa e incremental: planificación de sprint, ejecución, revisión del avance y retrospectiva. Aunque el backlog original plantea sprints de 2 semanas, para la ejecución individual se adoptó un ciclo operativo de 4 semanas para reducir sobrecarga administrativa y concentrar mejor el desarrollo.

Backlog orientado por valor

El trabajo se organizó a partir del Product Backlog y del Release Plan del proyecto, priorizando primero diseño técnico, arquitectura y contratos, y luego funcionalidades de seguridad, administración, auditoría y flujos de negocio visibles en el MVP.

2. Roles

Cómo se manejaron los roles siendo una sola persona

Los roles no desaparecen: se simulan con responsabilidades separadas.
Scrum Master

Se asume este rol al inicio y cierre del sprint. La función es ordenar el trabajo, revisar impedimentos, mantener el backlog actualizado y asegurar que se cumplan las ceremonias y la disciplina del proceso.

Developer

Se asume este rol durante la ejecución técnica. Aquí se diseñan pantallas, se desarrolla backend y frontend, se integra la base de datos, se validan criterios de aceptación y se documenta la evidencia del sprint.

Postura recomendada

En la sustentación conviene decir que los roles fueron simulados de forma controlada. No se presenta como un equipo ficticio, sino como un proyecto individual que aplicó Scrum adaptado, separando momentos de planeación, ejecución y evaluación.

3. Ceremonias

Cómo se desarrollan backlog, release y retrospectiva

Versión breve y defendible para una sustentación individual

Product Backlog

Es la lista priorizada de historias de usuario, tareas técnicas y entregables de diseño. En este proyecto el backlog se actualiza según valor, dependencias y viabilidad real de implementación.

  • Se refinan historias, criterios de aceptación y DoD.
  • Se reordena el trabajo según avance real del MVP.
  • Se usa como base para seleccionar el Sprint Backlog.

Sprint Planning

Al inicio del sprint se define qué historias se comprometen, cuál es el objetivo del sprint y qué entregables serán demostrables al final del ciclo.

  • Se priorizan ítems factibles en 4 semanas.
  • Se revisan dependencias técnicas y académicas.
  • Se define una meta concreta del sprint.

Sprint Review / Release

Al cierre se presenta lo construido, se contrasta con lo planeado y se identifican diferencias entre la planificación original y la implementación real.

  • Se demuestran funcionalidades visibles o artefactos técnicos.
  • Se revisa el cumplimiento de criterios de aceptación.
  • Se ajusta el Release Plan frente al avance real.

Sprint Retrospective

Espacio de mejora del proceso. En un proyecto individual sirve para detectar qué decisiones ayudaron, qué bloqueó el avance y qué ajustes deben hacerse en el siguiente sprint.

  • Qué funcionó: foco y avance técnico.
  • Qué no funcionó: sobreestimación o dependencias externas.
  • Qué cambiar: alcance y secuencia del siguiente sprint.
4. Cadencia

Ejemplo de sprint de 4 semanas

Adaptación práctica para un solo desarrollador
Semana 1 Planificación y diseño
  • Refinar backlog.
  • Definir objetivo del sprint.
  • Partir tareas técnicas y académicas.
Semana 2 Construcción principal
  • Desarrollo backend y frontend.
  • Base de datos y endpoints.
  • Primeras validaciones funcionales.
Semana 3 Integración y pruebas
  • Unión de módulos.
  • Revisión de criterios de aceptación.
  • Corrección de hallazgos.
Semana 4 Review y retrospectiva
  • Preparar demo.
  • Comparar plan vs ejecución.
  • Actualizar backlog y lecciones aprendidas.
En la exposición puedes decir que el sprint de 4 semanas fue una adaptación metodológica consciente, útil para equilibrar desarrollo, documentación y validación académica dentro de un proyecto individual.
5. Sprint 1

Sprint 1 finalizado: diseño técnico, arquitectura y base del flujo

Fuente: backlog Excel + tablero “Sprint 1 Finalizado” compartido

Objetivo del sprint

Construir la base conceptual y técnica del proyecto: modelado del proceso de negocio, arquitectura, contratos entre capas y primeros componentes del flujo documental e inteligencia artificial.

Duración adaptada: 4 semanas Enfoque: Diseño + preparación técnica Resultado: Base del MVP
DS-01 · Modelar el proceso de negocio completo de Smart Bills Cleaner

Incluye BPMN del flujo upload → OCR → validación → consulta NLP → reporte. Se alinea directamente con el tablero donde aparece “Modelar el proceso de negocio”.

DS-03 · Definir contratos de API entre capas

Se usó para formalizar cómo se conectan frontend, backend y servicios externos, y en el tablero aparece como “Definir contratos de API entre capas”.

DS-06 · Diseñar UI/UX del módulo de consultas NLP

Permite preparar la experiencia conversacional antes de la implementación completa del módulo de lenguaje natural.

DS-07 · Diseñar el flujo de Prompt Engineering para el LLM

Se enfoca en cómo estructurar contexto, pregunta y respuesta dentro del pipeline RAG del proyecto.

Tareas técnicas observadas en el tablero

Endpoint REST `POST /facturas/cargar`, almacenamiento temporal tipo S3 y diseño / despliegue de vectorización y base de datos vectorial como preparación del motor documental.

Entregables visibles del sprint

  • Diagrama BPMN del negocio.
  • Arquitectura por capas y flujo de datos.
  • Definición de contratos API.
  • Diseño de la experiencia NLP.
  • Base técnica inicial del flujo de carga y vectorización.

Ejemplo breve para decirlo

“En el primer sprint concentré el trabajo en la definición del proceso, la arquitectura y los contratos técnicos, porque eso me permitía reducir riesgo antes de desarrollar funcionalidades de seguridad y operación.”

6. Sprint 2

Sprint 2: seguridad, administración, auditoría y soporte al usuario

Fuente: tablero “Sprint 2” + HUs detalladas compartidas

Objetivo del sprint

Implementar la base de seguridad y gobierno del sistema: autenticación, gestión de usuarios, auditoría, administración y comunicación al usuario mediante correo o simulación funcional.

Duración adaptada: 4 semanas Enfoque: Seguridad + trazabilidad Resultado: Control de acceso del MVP
US · Inicio de sesión

Registro e inicio de sesión seguro con correo y contraseña, hash con bcrypt, JWT y el flujo proyectado de refresh token y recuperación de contraseña.

US · Roles de gestión de usuarios y seguridad

Gestión de roles `Admin`, `Analista` y `Viewer`, con control de permisos, restricción de acceso a facturas y registro de intentos no autorizados.

US · Gestión de administrador / auditoría

Registro de acciones sobre facturas: carga, consulta y eliminación, con usuario, acción, timestamp e IP, visibles desde un panel administrativo.

US · Auditorías y email communication

Notificaciones por correo cuando una factura es procesada o falla. Para la sustentación puede presentarse como implementado o simulado según el estado real.

Ítems observados en el tablero

“Roles de Gestión de Usuarios”, “Gestión de administración”, “user functions”, “Creación de reportes” y “Email comunication”.

Entregables visibles del sprint

  • Login y protección básica de acceso.
  • Gestión de usuarios desde frontend.
  • Auditoría de eventos del sistema.
  • Panel administrativo para revisión de logs.
  • Base de comunicación por correo o simulación del flujo.

Ejemplo breve para decirlo

“En el segundo sprint enfoqué el desarrollo en asegurar el sistema: identidad, roles, trazabilidad y comunicación al usuario, porque esto daba soporte al uso real del MVP y fortalecía el componente académico de seguridad.”

7. Postura

Qué decir en la sustentación siendo el único integrante

Mensaje corto, honesto y metodológicamente sólido

Postura recomendada

“El proyecto se desarrolló de forma individual, por lo que las prácticas Scrum se aplicaron de manera adaptada. Los roles de Scrum Master y Developer no fueron desempeñados por personas distintas, sino por mí mismo en momentos separados del proceso: primero para planificar y controlar, y luego para ejecutar y validar.”

Por qué esta postura funciona

  • No inventa un equipo que no existe.
  • Demuestra comprensión real del marco ágil.
  • Justifica la adaptación del sprint a 4 semanas.
  • Permite mostrar evidencia clara de planeación, ejecución y retrospectiva.
Frase de cierre sugerida: “Más que replicar Scrum de forma literal, apliqué sus principios de iteración, priorización, revisión y mejora continua de manera compatible con un proyecto individual.”
