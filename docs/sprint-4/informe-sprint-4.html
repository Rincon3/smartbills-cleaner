2. Cómo se desarrolló cada historia

SBC-15 — Vectorización y BD vectorial

Problema: los embeddings vivían en JSON y la similitud se calculaba en memoria. Decisión: PostgreSQL + extensión pgvector, columna InvoiceChunk.embedding vector(96), metadatos embeddingModel / embeddingDim, índice HNSW pequeño (dataset de demo, no estrés).

Flujo: al crear o editar una factura, chunkIndexService borra chunks previos y escribe vectores con SQL (replaceInvoiceChunks). El usuario no ve un botón de “indexar”.

Datos de prueba: seed DEMO-VEC-01 a 06 (acueducto, Claro, papelería, Terpel, Enel, Microsoft), 2 páginas c/u, más facturas ya cargadas. Modelo real: hashed-bow-96-v2 (no SBERT).

Archivos: migración 202610080001_pgvector_embeddings, vectorStore.js, chunkIndexService.js, semanticDemoInvoices.js, imagen Docker pgvector/pgvector:pg15.

SBC-29 / 30 / 31 / 32 — RAG

SBC-30: retriever LangChain sobre pgvector + cadena RunnableSequence (equivalente RetrievalQA en LangChain 1). Top-K = 5.

SBC-31: prompt en español, formato de cita obligatorio, 3 few-shots (NIT, total, “no hay evidencia”).

Consenso: modelo base vs ajustado (Bedrock Nova Lite/Pro si hay AWS; si no, respuesta local corta vs un poco más amplia). Gana la más fiel a las citas recuperadas. Si la API falla o no hay clave, no se rompe la consulta.

SBC-32: métricas tipo RAGAS en Node (fidelity, context precision/recall, answer relevancy) y script npm run eval:ragas sobre 5 casos DEMO. Última corrida documentada: promedio RAGAS ≈ 0.69, fidelidad 1.0 (sin Bedrock; generador local).

Archivos: services/rag/*, queryService.js, scripts/ragas-eval.mjs.

SBC-25 — Búsqueda híbrida

Criterios: texto + proveedor + fechas + rango de montos; SQL primero; ranking semántico; UI avanzada; objetivo < 4 s.

Diseño: parseSearchFilters → prisma.invoice.findMany (WHERE) → si hay q, searchSimilarChunks solo sobre esos IDs → colapsar chunks a facturas por máximo score.

API: GET /api/invoices/search (registrada antes de /:id). Respuesta: listado + elapsedMs + mode (sql o sql+pgvector) + withinSla.

UI: componente AdvancedSearchForm en Facturas (y filtros reutilizados en Consultas).

SBC-17 — DoD de Consultas NL

La pantalla ya existía; se cerró el DoD: citas clicables al fragmento (chunk_source), panel Sin evidencia verificable, bloque Fragmentos Top-5 siempre visible (N de 5), latencia en ms y marca “dentro de 4 s”. Pregunta de control: arriendo en Madrid → sin evidencia (no inventa una factura).

Archivos: ConsultPage.jsx, queryService.js (noEvidence, elapsedMs).

SBC-8 (parcial) — OCR nube opcional

Camino feliz sigue siendo local. Si el PDF no tiene texto suficiente: Document AI (si hay proyecto + processor + cuenta) → Textract (si hay keys AWS) → Tesseract. Sin claves o si la API falla, se omite el ramal y el upload continúa. No hay SQS. Orden configurable: OCR_CLOUD_ORDER=documentai,textract.

Archivos: ocr/cloudOcr.js, ocrEngine.js.
